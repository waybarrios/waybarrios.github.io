Systems notes · CUDA · Numerical fidelity

When custom CUDA beats vendor baselines

I measured custom CUDA projections against cuBLAS, cuBLASLt and PyTorch on a stock RTX 3070 Ti Laptop GPU. A fused lossless BF16 kernel saved 17.70 to 20.45% of GPU latency on the registered large single-token cases. Small native BF16 reductions reached 28.34 to 29.77% on one shape.

Wayner Barrios · 25 October 2026

These are streaming CUDA graph measurements on one SM86 GPU, with observed memory clocks of 810 MHz. The numbers describe GPU operations under this regime. Full-model throughput and energy savings remain unmeasured.

Projection shapes and numerical fidelity

The projection is Y = XWᵀ, with X[M,K] and W[N,K]. Small M is common during autoregressive decoding. I kept each tensor in its supplied dtype and required exact weight reconstruction. All kernels accumulate in FP32.

The native suite samples synthetic tensors directly in FP32, FP16 or BF16. FP32 weights stay FP32. Output checks use an FP64 reference and fixed tolerances of 1e-5 + 1e-4 × |reference|; BF16 output uses the corresponding rounded interval.

Two kernel families address different costs. Small projections use vectorized loads and warp reductions specialized for the shape. Large checkpoint projections decode losslessly packed BF16 weights inside the dot product, reducing weight traffic.

CUDA C++ · reduction structure, with indexing and vector loads omitted

float acc = 0.0f;
for (int k = lane; k < K; k += 32)
    acc = fmaf(x[k], weight[k], acc);

for (int offset = 16; offset; offset /= 2)
    acc += __shfl_down_sync(0xffffffffu, acc, offset);

The measured kernels handle native dtype loads and explicit output contracts. Their block sizes and vector widths were frozen before the held-out runs.

Small projections and the 10% criterion

The native-input suite contains six small shapes and three additional large FP32 shapes. Each dtype and power profile has three fresh processes. Filled points identify shapes that pass the complete three-process criterion; crosses retain the other results.

Under Performance on AC, eight dtype/shape combinations qualify. BF16 at 4×256×256 saves 28.34 to 29.77%. Native FP32 at 1×128×128 passes narrowly, with a lowest per-process confidence bound of 10.003%. Its large FP32 projections save 9.09 to 9.75%, below the acceptance target.

Fusing lossless decoding and projection

The checkpoint experiment uses original BF16 weights from Qwen/Qwen2.5-0.5B-Instruct and controlled synthetic BF16 activations. For each block of 64 weights, a coded block stores the sign, seven fraction bits and a four-bit exponent delta. Blocks whose exponent range does not fit keep their original BF16 bits.

A coded block occupies 96 payload bytes plus four metadata bytes, compared with 128 bytes for the original weights. The retained tensors occupy about 78.2% of their original storage, including raw fallback blocks and metadata. The CUDA kernel reconstructs each weight before its FP32 multiply-add.

CUDA C++ · decoder used by the measured kernel

__device__ __forceinline__ float cbf16_decode(
    unsigned code, unsigned base) {
    return __uint_as_float(
        ((code & 0x7fu) << 16) |
        ((code & 0x80u) << 24) |
        (base + ((code & 0xf00u) << 15)));
}

Here base already occupies the FP32 exponent bit positions. The code restores the fraction, sign and exponent without a lossy conversion. Both raw and coded templates use the same reduction order.

BF16 output passes all 27 primary cases at 17.70 to 20.45% latency saved. FP32 output passes 24 of 27; three vendor A/A controls fail in the last process. That combined milestone remains unaccepted.

The full grid contains 396 cases per output contract, including small K/V regressions and poor larger-M results. Small K/V currently uses a vendor fallback. A separate, bias-free M=1 K/V fusion experiment saves 20.43 to 20.67% with FP32 output by making one vendor call for both projections.

Timing protocol and statistical checks

Each timing uses a rotating physical weight ring of at least 80 MiB and 20 times L2. CUDA graph replay excludes packing, allocation and Python dispatch. The baseline pool includes original and transposed cuBLASLt layouts, strict FP32-compute cuBLAS, PyTorch, and FP32 GEMV where applicable. Every vendor route has its own independent A/A twin.

A shape qualifies only when every registered process passes the numerical and weight-bit checks, its winning vendor A/A difference stays within 1%, and its paired 95% latency-saved lower bound exceeds 10%. The bootstrap selects the best eligible vendor again in every draw. Native runs use seeds 971, 977 and 983; checkpoint validation uses 919, 929 and 937 on held-out layers.

Use a fresh registered study for new measurements. Failed runs and failed controls stay in the record; another run cannot replace them. Both system power profiles use AC power. The observed GPU regime was P5 with memory at 810 MHz even in Performance mode.

Latency savings and energy limits

The reported percentage is 100 × (1 − Tcustom / Tvendor). A sub-10% result can still save useful time. The large FP32 example drops from 4.486 ms to 4.049 ms, saving 0.437 ms. At the same measured streaming latency, one million operations would save about 437 seconds of GPU work. This is an extrapolation of operation time.

Energy is the integral of power over time. Equal average power would make percentage energy savings equal percentage time savings. The local total-energy counter failed a query-cadence check, so these experiments do not establish joules or kWh saved. Full-model timing and a qualified energy measurement remain open.

Reproducibility and open experiments

All results here use the stock GPU software state. A matched hardware-unlocked comparison is still pending. Other useful next steps include a faster custom K/V path, guarded integration into a model, and measurements at other memory-clock regimes.

The code and experiment protocols are in klab. Reproductions, numerical counterexamples and negative results are welcome. If you want to explore a case, open an issue with its shape, precision contract and baseline so we can discuss a useful comparison.
